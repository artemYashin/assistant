# Архитектура Orbit

## Решение и границы первого этапа

Orbit постепенно переходит на Feature-Sliced Design (FSD) на фронтенде.
Цель — понятные границы зависимостей и возможность менять одну область, не
переписывая соседние. Это внутренний рефакторинг действующего приложения.

Первый этап от 27 октября 2026 года сохраняет поведение: переносит независимые
модули, вводит публичные точки входа и автоматическую проверку импортов.
Он **не означает**, что всё приложение уже соответствует FSD.
Сервер пока сохраняет прежнюю структуру. Разделение Agent, маршрутов и Store —
последующие отдельные задачи, с самостоятельными проверками.

## Слои фронтенда

Импорт разрешён из верхнего слоя в нижний:

```text
app → pages → widgets → features → entities → shared
```

| Слой       | Ответственность                                 | Что перенесено сейчас                                                                                                                   |
| ---------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `app`      | Сборка приложения, провайдеры, маршрутизация    | App, Workspace, useWorkspace и конфигурация навигации                                                                                   |
| `pages`    | Композиция конкретной страницы                  | `updates`: страница «Что нового» и её CSS                                                                                               |
| `widgets`  | Самостоятельные блоки, используемые приложением | Начало `assistant`: управление размером панели и существующие функции предпочтений                                                      |
| `features` | Пользовательские действия                       | `read-updates`: отметка просмотренной версии                                                                                            |
| `entities` | Общие понятия продукта и их модели              | `developer`: группировка статусов и доступ к расчёту отпусков; `chat`: группировка истории                                              |
| `shared`   | Общие компоненты и технические функции          | Числовой ввод, селекты, подтверждения, аватар, информационное окно, кнопка сохранения; пагинация, zoom, drag-scroll и закрытие диалогов |

`src/main.tsx` — только запуск React и подключение `app/index.ts`.
Внутри среза используются сегменты по назначению: `ui`, `model`, `api`, `lib`.
Создавать пустые сегменты и дробить каждую кнопку на отдельную feature не нужно.
Код, нужный только одной странице, сначала остаётся в этой странице.

## Правила зависимостей

1. Между срезами импортируем публичный `index.ts` (в NodeNext-путях — `.js`).
   Внутри одного среза допустимы прямые относительные импорты.
2. Срезы одного слоя `pages`, `widgets`, `features`, `entities` не импортируют
   друг друга. Композицию выполняет более высокий слой.
3. `shared` не знает про тикеты, разработчиков, память и HTTP-маршруты конкретных
   функций. Его UI-компоненты получают данные и callbacks через props.
4. В `shared` используются отдельные публичные входы компонентов/библиотек,
   например `shared/ui/number-input/index.ts`; общего barrel на весь UI нет.
5. Используем относительные пути с расширением `.js`, сохраняя текущую настройку
   TypeScript NodeNext. Новые alias и новый сборщик сейчас не вводятся.
6. Не складываем продуктовую логику в `shared/lib` ради обхода зависимостей.
   Общий сценарий сначала требует определения владельца.
7. Серверный код не импортирует React UI. Общие клиент-серверные модели
   выделяем отдельным этапом; не переносим серверные зависимости в браузер.

Проверка: `npm run architecture:check`, также входит в `npm run check`.
Она проверяет обычные/динамические импорты, re-export, type imports и URL модулей.
TypeScript и Vite дополнительно проверяют разрешение модулей и сборку.

## Переходный код и исключения

Большинство старых файлов пока лежат непосредственно в `src/`. Это временная
граница миграции, а не новый рекомендуемый стиль. `scripts/architecture-policy.json`
содержит точный список таких файлов и разрешённых зависимостей нового слоя от старого.
Новые корневые TS/TSX-модули проверка запрещает.

Исключения первого этапа:

- `app/legacy-workspace.tsx` содержит прежнюю сборку приложения, страницы и
  ассистента. Перенос не разделяет их состояния и не меняет порядок хуков.
  Этот файл временно импортирует старые компоненты, стили и серверные модели.
- `entities/developer/model/vacation.ts` продолжает использовать существующие
  чистые расчёты из `server/developer-vacation-status.ts`. Единственный источник
  правил сохраняется; копию этих расчётов не создаём.
- `shared/config/releases/index.ts` читает прежний `src/releases.json`, на который
  опираются правила версий и проверка релизов.

Исключения не разрешаются маской на весь каталог. При следующих переносах
уменьшаем список. Расширение требует объяснения в описании изменения.
Старые модули уже используют публичные входы перенесённых компонентов.

`scripts/fsd-moves.json` фиксирует исходные и новые пути первого этапа.
Генератор справки использует его для сохранения прежних ID автоматических статей;
ссылки на исходники и отпечатки обновляются. Это карта **исходного кода**, не
миграция пользовательских файлов. Не удалять её без сохранения стабильных ID.

## Сервер: дальнейшее направление

Планируем модули `chat`, `tickets`, `calendar`, `developers`, `memory`,
`pull-requests`, интеграции Azure/Copilot/Git и инфраструктуру БД/файлов/HTTP.
Пока этих каталогов нет: первый этап их не имитирует пустыми папками.

HTTP-маршруты и инструменты ассистента должны вызывать общие операции.
Чат и review сохраняют независимые Agent instances, отмену и состояния.
Контекст выполняющегося запроса должен принадлежать запуску, а не текущему
выбору UI. Изменять этот механизм в рамках перемещения файлов нельзя.

## Совместимость с существующими установками

В первом этапе не меняются:

- таблицы SQLite, миграции, SQL и данные;
- настройки, ключи и значения localStorage, фильтры и наборы;
- ID, URL страниц и API, названия событий браузера;
- папки хранения, вложения, Docker bind mounts;
- история чатов, память, локальные поля тикетов, завершения и повторения;
- формы, CSS-классы, условия действий и подтверждений;
- версия приложения и история релизов: внутренний перенос без новых возможностей
  не требует пользовательского релиза.

Миграция данных для этого этапа не нужна: пути исходных файлов не используются
как новые ключи пользовательского хранилища. Проверки работают с временными БД
и вымышленными данными. Рабочее хранилище пользователей не открываем и не очищаем.

При будущем изменении формата хранения миграция или совместимый reader входят
в то же изменение. Обязательно проверять заполненную старую БД, повторный запуск
и сохранение связей/вложений. Гарантировать сохранность данных только по успешной
сборке нельзя.

## Порядок следующих переносов

1. Выделять по одному связанному участку из временной сборки приложения.
2. Сначала переносить с прежними интерфейсами, не менять одновременно алгоритм.
3. Убирать соответствующие legacy-исключения и переходные импорты.
4. Проверять `architecture:check`, TypeScript, production build и профильные тесты.
5. Проверять браузером страницы, диалоги, события и localStorage; отдельно workers
   и ресурсы при изменении их путей.
6. Изменения поведения делать отдельным этапом с обновлением справки и релизов.

Текущее ограничение: проверка границ не заменяет проверку поведения и не
контролирует каждую зависимость внутри оставшихся legacy-файлов.

## Второй этап: модели и повторно используемые компоненты

Продолжение от 27 октября 2026 года переносит ещё 29 модулей:

- `entities/calendar`: время, статусы, сортировка, раскладка событий, минутные
  обновления, выбор даты и поля предварительного предупреждения;
- `features/filter-calendar` и `features/filter-pull-requests`: модели фильтров;
- `entities/ticket`: текст и ссылки тикетов, подсветка цитат, дата и копирование ID;
- `features/export-tickets`: выбор столбцов, имя файла, CSV, Markdown, clipboard,
  Excel. Отдельный публичный вход `xlsx/index.ts` сохраняет динамическую загрузку
  ExcelJS: основной `index.ts` намеренно не экспортирует Excel;
- `entities/chat`: разбор карточек PR и анализа тикетов;
- `entities/repository`: тип файла, ветка и ссылка на конкретную версию diff;
- `entities/note`: расчёт бюджета изображений;
- `shared/config/routes`: существующий контракт внутренних URL, включая проверку
  ссылок на код; `shared/lib/time-zone`: варианты часовых поясов.

Существующие серверные расчёты календаря и описание столбцов экспорта остаются
единственным источником правил. Восемь точных зависимостей на эти чистые модули
и типы добавлены в allowlist до отдельного выделения общих моделей. Это не
разрешение импортировать произвольный серверный код. Новых зависимостей между
срезами одного слоя не добавлено.

Содержимое функций, React-состояния, строки UI и хранилищ не меняются. Миграция
пользовательских данных не требуется. Исходные ID статей справки сохранены через
карту переносов. Большие страницы и связанные с ними сценарии пока остаются в
переходной структуре; это продолжение миграции, а не её завершение.

## Третий этап: настройки таблиц и голосовой ввод

Ещё 21 модуль переносится с прежними интерфейсами:

- `features/filter-tickets`: фильтры, наборы, панель и загрузка вариантов;
- `features/ticket-columns`: порядок/видимость столбцов, ширины и resize;
- `entities/ticket`: выделение строк, просмотренный тикет и легенда цветов;
- `entities/work-mode`: общий React-контекст режима Lead/Developer;
- `entities/workspace`: сохранение выбранного контекста;
- `features/voice-input`: сочетания клавиш, overlay и компоненты голосового ввода;
- `features/filter-pull-requests`: хук фильтров;
- `entities/developer` и `entities/repository`: имена порученных разработчиков
  и подпись ветки; `shared/ui/last-sync`: отображение последней синхронизации.

Контекст режима работы и состояние выделенных тикетов остаются единственными
экземплярами модулей: публичные входы переэкспортируют их, а не создают копии.
Старый HTTP-клиент пока сохраняется в `src/api.ts`: он совмещает общий транспорт
и наблюдение за запущенным чатом. Для фильтров и голосового ввода разрешены две
точные временные зависимости на него. Ещё четыре зависимости сохраняют общие
серверные правила режима работы и горячих клавиш. Это задокументированные
переходные связи; транспорт и общие контракты будут выделяться отдельно.

Существующая логика совместимого чтения старых фильтров, имена browser events,
ключи столбцов/ширин/контекста и настройки голоса сохранены буквально. Новых
миграций данных и пользовательского релиза для переноса не требуется.

## Четвёртый этап: diff и подсветка кода

В `entities/repository` перенесены 10 модулей: разбор/метаданные diff, выбор
языка подсветки, highlighter, три workers, дерево файлов, список коммитов и
компоненты фрагментов кода Markdown.

Публичные входы разделены по среде выполнения:

- `index.ts`: модели diff, языки и обычные компоненты репозитория;
- `highlight/index.ts`: подсветка для прямого использования и её типы;
- `snippet/index.ts`: отображение подсвеченного кода в Markdown;
- `workers/*.worker.ts`: самостоятельные входы Vite Worker. Их никогда не
  переэкспортируем из обычного index: обработчик `self.onmessage` должен
  устанавливаться только в соответствующем worker.

Три точных зависимости от CodeBrowserPage, PrDiffDialog и RepositorySearch на
worker-файлы разрешены в architecture-policy. Это исключение из правила barrel
для самостоятельных исполняемых ресурсов, а не для обычных импортов. Сохраняются
статические `new Worker(new URL(..., import.meta.url))`, нужные Vite, и прежние
имена worker assets. Внутри среза дерево файлов импортирует модуль иконок напрямую,
чтобы не создавать цикл через собственный публичный index.

Расчёты, сообщения worker, таймауты, хранение выбранного языка и результаты
подсветки не меняются. Миграция пользовательских данных не нужна.

## Пятый этап: календарь и страницы отчётов

Перенесены ещё 10 модулей, включая целые страницы:

- `pages/calendar`: страница календаря/напоминаний и её временная сетка;
- `widgets/calendar-notifications`: уведомления в хедере и всплывающий блок;
- `features/complete-reminder`: завершение текущей итерации напоминания;
- `features/configure-calendar`: настройки календаря;
- `entities/schedule`: редактор расписания, общий для синхронизации и уведомлений;
- `pages/usage`: страница использования LLM;
- `widgets/overview-activity`: история действий и её текстовые описания;
- `widgets/overview-usage`: сводка использования на главной странице.

Страница календаря пока сохраняет внутреннюю композицию: формы, операции и
состояние не разделяются одновременно с переносом. Временная сетка остаётся
локальным компонентом страницы. Уведомления — отдельный widget, потому что
живут в оболочке приложения независимо от открытой страницы. Завершение
итерации — общая feature для уведомлений и страницы, без межстраничных импортов.

Тринадцать точных переходных связей сохраняют прежние зависимости на `src/api.ts`
и чистые серверные модули `calendar-model`, `calendar-repeat`,
`calendar-notifications`. Дублирующиеся импорты одной зависимости учитываются
один раз. Они перечислены в architecture-policy, а прежние связи оболочки на
перемещённые корневые компоненты удалены. Следующим самостоятельным этапом
следует выделить транспорт и общие контракты, чтобы сократить этот allowlist.

Маршруты, обработчики событий, poll-интервалы, завершение повторений, ключи
фильтров и настройки уведомлений сохранены. Перенос не требует миграции данных
или пользовательской записи в истории релизов.

## Шестой этап: заметки, комментарии и изображения

Перенесены ещё 9 модулей:

- `pages/notes`: свободные заметки и вкладка заметок тикетов;
- `features/edit-ticket-note`: редактирование заметки тикета;
- `features/comment-ticket`: отправка комментария с отложенной загрузкой картинок;
- `entities/rich-content`: существующий редактор форматированного содержимого,
  просмотр изображений и действия с изображением;
- `features/attach-chat-image`: очередь подготовки изображений для чата;
- `features/voice-input`: диктовка в поле.

У rich-content два публичных входа: `editor/index.ts` и `preview/index.ts`.
Превью не импортирует редактор TipTap. Внутри среза используются прямые импорты,
а не собственный barrel. Действия с изображениями пока сохраняют прежнюю
продуктовую логику получения исходной ссылки и browser event прикрепления к
чату; поэтому эти компоненты не объявлены универсальными shared/ui.

Шесть точных временных зависимостей на старый `src/api.ts` сохранены для
заметок, комментариев, исходной ссылки изображения и очереди прикрепления.
Перенос не меняет загрузку/очистку файлов, Map черновиков, blob URL, ревизии
заметок, защиту несохранённого текста или событие `orbit:attach-image`.
Пути пользовательских вложений не перемещаются. Миграция данных не нужна.

## Седьмой этап: транспорт и операции репозитория

Общий клиент из `src/api.ts` перенесён в `shared/api/http`: JSON, FormData,
CSRF и чтение NDJSON. Состояние CSRF находится в одном модуле; чат и операции
репозитория используют тот же транспорт. Все временные исключения зависимостей
на `src/api.ts` удалены.

Сценарий создания/наблюдения чат-запуска выделен в `entities/chat/api` с отдельным
публичным входом. `followChatRun` сохраняет курсор, повтор при сетевой ошибке,
порядок событий и отмену. Чатовый `apiProgress` сохраняет прежнюю ветку
`/conversation`, остальные пути делегирует общему транспортному `apiProgress`.
Код репозитория использует общий потоковый клиент напрямую. Общий слой больше
не знает маршрутов и жизненного цикла чата.

Также перенесены `features/repository-jobs` (прогресс и список Git-операций) и
`features/search-repository` (поиск). Исключение worker URL поиска перенесено
на новый файл владельца. Контракты API, лимиты ответа, polling-интервалы,
сообщения ошибок и заголовки запросов остаются прежними.

Это выделение границ, а не изменение поведения. Данные и схемы не меняются,
миграция не нужна. Публичный API HTTP не содержит специфичной для чата ветки;
внутренние потребители перенаправлены на соответствующие точки входа. Прежний
ID статьи ошибок api.ts сохранён картой переноса, ошибки сценария чата теперь
индексируются также по его отдельному исходнику.

## Восьмой этап: pull request

Перенесены 15 модулей:

- `pages/pull-requests`: активные и завершённые PR, общая композиция карточек;
- `widgets/pull-request`: действия/счётчики, здоровье PR, CI, создание,
  коммиты, merge, запуск review и связанные тикеты;
- `features/view-diff`: общий просмотр diff для PR и коммитов репозитория;
- `entities/llm`: выбор модели; `entities/azure-user`: выбор пользователей Azure,
  используемый также настройками импорта и репозитория;
- `widgets/review-questions`: вопросы ревью в подтверждениях.

Общий diff находится ниже widgets и pages: список коммитов PR и репозиторий
используют один компонент и один существующий Map кэша. Внутри PR widget
диалоги используют прямые относительные импорты. Исключение worker URL diff
перенесено на новый путь владельца, без добавления альтернативного worker.

Семь временных связей оставлены явно: правило merge из server/pr-health,
ChatTools, ChatMarkdown, TicketMetadata и три использования TicketControls.

## Размещение сервисов и единые инструменты

Корень репозитория содержит Compose, общий package.json/lockfile, конфигурации,
тесты и документацию. Исходники находятся в services/frontend/src (прежний src),
services/backend/src (прежний server), services/code-browser и services/voice.
Упоминания src/server в описаниях прежних этапов выше — исторические пути.
Слои FSD и их границы не изменились. Отдельные npm-пакеты/workspaces пока не
вводятся: UI и backend по-прежнему собираются совместно, Git и voice — отдельные
контейнеры. Это сохраняет существующую модель зависимостей и поставки.

ESLint использует flat config и рекомендуемые JS/TS-проверки; Prettier отвечает
за форматирование без конфликтующих ESLint-правил. Явные any и неиспользуемые
переменные пока не запрещены для существующего кода. Rules of Hooks — ошибка,
exhaustive-deps — ошибка. Проверка ESLint не допускает предупреждений. Исключения для очистки управляющих символов
и тестового перехвата this локальны и имеют пояснения. Настройка новых инструментов
не является поводом менять зависимости эффектов или бизнес-логику.

Bind mounts и локальный DATA_DIR не перемещались. Документация остаётся в
корневом docs/help и доступна backend как в dev, так и в собранном Docker runtime.
Сборка/запуск выполняются из корня. Миграции данных для переноса кода не нужны.

Плавная сортировка вертикальных списков указателем вынесена в `shared/lib/pointer-sort`: настройки канбана, отображение столбцов и экспорт используют один хук. Хук не знает о тикетах или настройках и сообщает перемещение индексов; сохранение порядка остаётся в соответствующем срезе.

Форма создания Azure-тикета находится в features/create-ticket: её используют оболочка попапа на странице тикетов и встроенная панель виджета деталки. Связь с текущим тикетом задаётся начальным параметром формы; API, загрузка изображений, кэш типов и локальный ключ последнего типа общие.

Общий редактор бейджей тегов расположен в `shared/ui/tags-editor`: получает значения,
подсказки, лимиты и подпись через props, не знает HTTP-маршрутов или доменных сущностей.
Загрузка локальных подсказок остаётся в `features/edit-ticket`, а формы создания и
редактирования Azure используют тот же UI. Старый путь редактора сохранён в
`scripts/fsd-moves.json` для стабильных идентификаторов справки.
