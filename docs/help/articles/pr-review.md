# Запуск и остановка AI review

## Запуск
Откройте «Запустить ревью». Выберите модель (или default), частоту вопросов, общий бюджет токенов, контекст и комментарий ревьюеру.
Частота вопросов: без вопросов, только важные (до трёх), подробные (до восьми). Вопросы появляются для уточнения; ответы продолжают то же ревью.
## Контекст
«Разрешить поиск и чтение кода репозитория» включает дополнительные локальные инструменты. Перед ревью готовится source-ветка; без этой галочки этап подготовки Git не нужен. Иконка/tooltip объясняет готовность.
Глубина: Низкая — diff и точечная проверка существенного риска; Ниже среднего (default) — изменённая логика и ближайший контекст; Средняя — контракты/вызовы/граничные случаи; Высокая — шире зависимости/примеры, больше токенов. Это инструкции модели, не жёсткие серверные квоты на чтение.
«Прочитать связанные тикеты, комментарии и локальные заметки» включено по умолчанию, если есть учитываемые связи. Нет связей/все исключены — выключено. Включение показывает список чекбоксов; выберите только релевантные, максимум 20. Можно снять/выбрать все. Исключённые локально связи не попадут в ревью.
## Память и лимиты
Выберите общую, заказчика, проекта, project review. Ревьюер получает ID и краткие описания, детали читает по инструменту. Один контекст сохраняется между файлами/вызовами/продолжениями; прочитанный материал не должен исчезать после каждого файла.
Бюджет вход+выход на всё ревью по умолчанию 1 000 000; задаётся в Настройки → Code Review и копируется в форму. Это отдельный лимит от чата. Максимум инструментов на ревью тоже отдельный (default 30). Учёт по отчётам SDK: последний вызов может превысить остаток, это не точный предварительный расчёт.
## Выполнение и результат
Состояния включают подготовку Git, очередь, выполнение, вопросы, готово, ошибку/остановку/устаревшую версию. «Остановить review» видна при выполняющейся работе. Не запускайте дубликат, не проверив состояние.
Результат показывает токены, замечания и при необходимости Markdown-код решения. Улучшения не обязательны для каждого PR. Ссылки на строки открывают нужную ветку/файл; цитаты тикетов — оригинал требования, если чтение тикетов разрешалось.
Log Review содержит параметры/результаты инструментов и доступные usage-данные только последнего PR-ревью глобально. Это не архив логов каждого PR; сами результаты ревью сохраняются отдельно.

Новый ручной запуск, в том числе повтор после ошибки или тайм-аута, получает отдельный ID, контекст и бюджет: токены предыдущих запусков к нему не прибавляются. Продолжения после ответов на уточнения относятся к тому же ревью; их входные и выходные токены суммируются в результате. Исторические записи, уже объединённые прежней версией приложения, автоматически не пересчитываются. Время одного запроса задаётся отдельно: Настройки → Code Review → Лимиты ревью → «Лимит времени ответа ревью, секунд» (по умолчанию 600; от 15 до 86 400). Подготовка Git и сбор diff в этот таймер не входят.

В попапе результата ревью нет вложенной карточки: модель, дата, покрытие, расход токенов и сведения о предыдущей версии собраны в компактной верхней части, отделённой тонким разделителем. Ниже расположен сам Markdown-отчёт со ссылками на код и тикеты.

Оформление свободное: ревьюер может чередовать обычные абзацы, списки, код и блоки замечаний, а предложения по упрощению размещать в любом подходящем месте. Дополнительная карточка оформляется обычным Markdown-заголовком «### Проблема: …», «### Замечание: …» или «### Улучшение: …» и абзацами под ним, без внешней цитаты. Интерфейс отделяет заголовок карточки тонкой линией. Цитаты тикетов, ссылки и код сохраняются. Это необязательные возможности, а не фиксированный шаблон всего отчёта.

Если при запуске разрешён поиск и чтение кода, предлагаемый пример ограничен 15 строками (желательно до 10). Более длинное исправление описывается словами со ссылкой на существующий участок кода в source-ветке, без разбиения примера на множество блоков. Если доступ к коду выключен, ограничение 15 строк не применяется: ревьюер может привести более длинную цитату из переданного diff или пример исправления, когда это нужно для понимания. Недоступное содержимое файлов не выдумывается.

Подписи **Критичность:**, **Проблема:** и **Предлагаемое решение:** получают небольшие иконки. При указанной критичности интерфейс показывает бейдж: критическая — тёмно-красный, высокая — красно-оранжевый, средняя — оранжевый, низкая — жёлтый, очень низкая — зелёный. Текст сохраняет смысл без цветов. Модель объясняет влияние, отличает дефекты от гипотез и необязательных улучшений, проверяет запутанную/избыточную логику и необоснованные константы. Всё ревью пишется простым человеческим языком; улучшения ради количества не требуются.

История ревью открывает компактный список запусков с версией, датой, статусом, моделью и известным расходом токенов. Нажатие на строку открывает результат в отдельном попапе с тем же оформлением, что у текущего ревью. Крестик или Escape закрывают только результат и возвращают к списку; следующий Escape закрывает историю.

Синхронизация и обновление PR не блокируются на время ревью. Ревью привязано к исходным SHA source/target: diff и чтение кода используют эту версию. Перед началом проверки актуальная версия сверяется с Azure; при несовпадении запуск помечается устаревшим. Уже выполняющийся анализ не отменяется обычным обновлением: его результат остаётся у исходной версии и доступен в истории; при обновлённых SHA он не считается ревью новой версии. Ссылки на код в текущем и историческом отчёте закреплены за source SHA соответствующего ревью. Даже старые ссылки без revision при отображении получают SHA сохранённого результата. Они не переключаются на актуальную версию ветки. Для новой версии нужен новый запуск.

Перед отправкой запроса модели версия PR повторно сверяется с Azure после подготовки Git и контекста. Если source или target изменились, результат подготовки помечается устаревшим и требуется синхронизация/новый запуск. При доступе к коду локальная source-ветка должна соответствовать SHA PR, иначе запуск не продолжается. Проверенный коммит закрепляется отдельной Git-ссылкой; дальнейший Pull не меняет содержимое ревью.

## Живой статус
Над кнопками карточки активного PR во время работы модели показывается «Анализирую изменения». Отдельные чтения памяти, поиск и чтение кода не меняют эту подпись. Когда модель начинает выдавать текст ответа, появляется «Готовлю результат». Это сигнал появления текста, а не гарантия, что инструменты больше не потребуются: если модель продолжит работу инструментами, статус вернётся к анализу. Текст самого отчёта сохраняется после завершения ревью.
Рядом вращается лоадер; при ожидании ваших ответов вместо него показана иконка вопроса. Подготовка Git, загрузка diff и чтение связанных тикетов до вызова модели сохраняют свои подписи. Карточка обновляется раз в 5 секунд: очень короткие этапы могут не попасть на экран. Хедер с общим состоянием ревью остаётся. Размышления модели не показываются.
Во время подготовки, очереди, анализа или ожидания ответов на месте «Запустить ревью»/«Повторить ревью» находится «Остановить ревью». Отдельной кнопки остановки в хедере нет. После окончания или остановки живой статус исчезает, и снова доступна кнопка запуска. Статус не зависит от сохранности Log Review и не вызывает дополнительных запросов к Azure или LLM.

Если обработчик занят другим ревью, ожидающий PR показывает «Ожидание завершения другого ревью» и в хедере, и над кнопкой остановки. Это относится и к заданиям с разрешённым чтением кода: до фактического начала обработки они не показывают подготовку Git. Когда обработчик свободен, но запуск ещё не начат, показывается «Ожидаю запуска ревью».

Для содержательных замечаний ревьюеру настоятельно рекомендуется карточка: короткий заголовок, критичность, описание проблемы/влияния и предлагаемое решение. В инструкции есть пример Markdown, который интерфейс распознаёт как карточку с иконками и цветной критичностью. Порядок замечаний и пояснений остаётся свободным; отсутствие проблем не требует придумывать карточки. Помимо цитаты `> ### Проблема: …`, поддерживается обычный заголовок `### Проблема: …` (также «Замечание» и «Улучшение»): блок продолжается до следующего заголовка того же/старшего уровня или следующего замечания. Подписи «Критичность:», «Проблема:», «Предлагаемое решение:»/«Решение:» в начале абзаца распознаются и без жирного Markdown.

Подключённый Git не заменяет короткий код ссылками: полезные примеры на 3–5 строк рекомендуется сразу показывать fenced-блоком с языком и подсветкой, а проверенную ссылку на исходник размещать рядом. Сохраняется ограничение до 15 строк предложенного примера при доступе к коду. Цитаты требований тикета остаются отдельными цитатами с переходом в тикет. Новые рекомендации применяются к следующим вызовам ревью; сохранённые отчёты не переписываются моделью задним числом.

Чат и ревью выполняются отдельными экземплярами общего Agent. Занятость чата не задерживает запуск ревью; остановка одного не прерывает другой. Несколько ревью по-прежнему идут по очереди. Git-кэш общий, чтение ревью привязано к коммиту. См. [инструменты ревью](review-agent-tools.md).

Карточки замечаний в новых ответах рекомендуются через обычный заголовок «### Проблема: …», «Замечание: …» или «Улучшение: …» и абзацы под ним: интерфейс сам оформляет их в карточку. Маркер цитирования > используется только для точной цитаты тикета с её ссылкой; вложенные цитаты >> и повтор одной цитаты не рекомендуются. Старый формат карточек через blockquote остаётся совместимым; сохранённые ответы не переписываются.

## Небольшие улучшения и договорённости проекта

Ревьюер рассматривает не только критичные ошибки, но и полезные замечания низкой критичности: повторение логики, запутанные условия, вводящие в заблуждение имена, неиспользование подходящего общего решения. Для замечания нужны конкретное место, практическая польза и соразмерное исправление. Однотипные случаи объединяются; вкусовые придирки, чисто косметические правки и выдуманные замечания ради количества не нужны. Дополнительная проверка использует уже изученный код и не отменяет выбранную глубину, разрешения и бюджеты ревью.

Если код расходится с выбранной памятью, ревьюер должен проверить детали соответствующей записи, её область действия и исключения. В результате он называет запись и её ID, если доступен, объясняет договорённость, фактическое поведение кода и пользу исправления: «В проекте договорились делать X; здесь сделано Y». Рекомендации отличает от обязательных правил, а неподтверждённые или устаревшие договорённости не выдаёт за доказанный дефект. Все записи подряд ради этого не загружаются. Эти рекомендации действуют на новые ревью; сохранённые результаты не переписываются.

## Код как доказательство замечания

Ревьюеру рекомендуется подкреплять наиболее полезные конкретные замечания коротким точным фрагментом существующего кода (обычно 3–5 строк) с подсветкой и проверенной ссылкой на строки, когда она доступна. Цитата требования тикета не заменяет объяснение, где именно реализация с ним расходится. Предложенный вариант исправления отделяется от исходного кода, чтобы их нельзя было перепутать.

Перед завершением отчёта с замечаниями по коду ревьюер проверяет, не остались ли в нём только цитаты тикетов и общие слова: при необходимости добавляет фрагмент или ссылку из уже доступного diff/прочитанного кода. Это рекомендация по содержательности, а не обязательная цитата в каждом пункте или повод читать весь репозиторий. Если обоснованных замечаний нет, цитаты не добавляются ради количества. Разрешения, ограничения длины примеров и привязка ссылок к проверенному коммиту сохраняются.

## Лимиты отдельного запуска

В окне запуска ревью поля «Максимум токенов на ревью» и «Максимум инструментов на ревью» расположены рядом, подписи — над полями. Они подставляются из «Настройки → Code Review → Лимиты ревью». Можно изменить их только для текущего запуска, без изменения общих настроек. Максимум инструментов — число вызовов, а не число разных инструментов; допустимо от 1 до 1000. Токены — входящие и исходящие за всё ревью, допустимо от 1000 до 100000000.

Оба лимита сохраняются с заданием и учитывают продолжения после вопросов. Достижение лимита вызовов останавливает ревью с сообщением: для нового запуска увеличьте «Максимум инструментов на ревью». Уже использованный бюджет при продолжении не обнуляется. Старые сохранённые задания без индивидуального лимита инструментов используют настройку Code Review; существующая история и результаты сохраняются.

## Бюджет и комментарий в результатах

Рядом с токенами в результате и в истории показано «Инструменты: использовано / лимит». Вызовы суммируются по запросам именно этого запуска, включая продолжения после вопросов; очистка подробного Log Review не сбрасывает счётчик. Если данные сохранились лишь частично, это отмечается. Неизвестный расход или исторический лимит обозначается «—»: текущая настройка не подставляется вместо неизвестного прошлого значения. Для старых ещё не начавшихся заданий фактический лимит сохраняется при запуске.

Если при запуске был указан комментарий ревьюеру, в шапке результата есть кнопка «Комментарий». Сам текст не показывается в результате, строке истории или подсказке кнопки. Нажатие открывает отдельный попап «Комментарий к ревью» поверх результата; «Закрыть» или Escape возвращает к результату, а не закрывает всю историю. Комментарий отображается как обычный текст с переносами строк, без выполнения Markdown/HTML. Если комментария нет, кнопки нет. Это скрывает текст интерфейса до нажатия, но не ограничивает доступ к сохранённым данным.
