# Docker и локальные данные

Orbit работает вместе с отдельными voice и code-browser сервисами согласно compose.yaml. Node-бэкенд хранит локальную SQLite-базу и секреты в каталоге данных; Git-сервис имеет отдельное хранилище кода.
Docker build использует npm ci для воспроизводимой установки зависимостей по lockfile. Python/make/g++ нужны стадии сборки native-модулей; это не установка при каждом открытии страницы. Изменение базового образа/зависимостей/слоёв или очистка Docker-кэша может сделать rebuild медленным.
Обычный git pull обновляет исходники, но не пересобирает уже работающий образ автоматически. Выполняйте принятый процесс обновления compose; не удаляйте volumes ради обновления интерфейса.
Данные/ключ шифрования должны сохраняться вместе. Потеря ключа не лечится новым PAT для всех старых секретов. Не публикуйте .env, базу и master.key.
Справка docs/help поставляется в runtime-образе. После обновления приложения сервер получает соответствующую версию статей; изменение MD в исходниках требует доставки в контейнер/перезапуска.
Если контейнеры приостановлены при сне Mac, фоновая синхронизация и загрузка тоже не продвигаются. Сверяйтесь со статусом сервиса и текущей работы, а не только с процентом.

## Папки Docker и миграция
Compose хранит данные в docker-data/ внутри проекта: orbit — база, master.key и данные Orbit; repositories — Git-кэш; repo-control — внутренний ключ сервисов; whisper — модели голоса. Эти папки исключены из Git и контекста Docker build. Пути фиксированы относительно compose.yaml, а не текущей папки терминала.
Для переноса старой установки запустите `bash scripts/migrate-docker-storage.sh` из проекта, при нестандартном имени добавьте `--project ИМЯ`. Нужен запущенный Docker. Скрипт находит реальные volumes, останавливает сервисы, копирует с сохранением прав и симлинков, проверяет SHA-256 файлов и запускает новый Compose. Заполненные целевые папки не перезаписывает; исходные volumes не удаляет. При ошибке копирования сервисы остаются остановленными, прежние volumes сохранены. Инструкция и откат — docs/DOCKER_STORAGE.md.
Для новой установки без старых данных используйте `bash scripts/migrate-docker-storage.sh --init`: создаст пустые папки с правами сервисов. Обычный `docker compose up -d --build` применяется после подготовки/миграции. Не меняйте владельцев всех папок на одного пользователя: Orbit/Git используют UID 1000, voice — UID 10001. Базу и master.key переносите и резервируйте вместе; содержимое docker-data нельзя публиковать.

Если перенос остановился с `Copy/verification failed`, исходный volume сохранён. Обновите скрипт и запустите `bash scripts/migrate-docker-storage.sh --diagnose` для чтения последней промежуточной копии без новой загрузки/копирования. Старые сервисы должны быть остановлены. Диагностика различает ошибки данных и несовпадение прав/владельцев, не печатает имена или содержимое файлов. Для возврата к прежним данным можно запустить `docker compose -f compose.named-volumes.yaml up -d` с прежним именем проекта.

Если диагностика показывает только `METADATA_MISMATCH` при совпадающих файлах/симлинках, используйте обновлённый скрипт с `--resume`. Он не перезаписывает готовую копию: повторно проверяет её содержимое, настраивает права копии и тестирует реальный доступ от UID сервисов отдельными контейнерами. Несовпадение UID/GID с Linux-volume само по себе больше не блокирует перенос на файловую систему хоста; неверные данные или недоступность файлов для сервиса продолжают блокировать запуск. Исходные volumes остаются только для чтения и не меняются.

При `FILESYSTEM_ERROR: EACCES` миграция останавливается, исходные volumes сохраняются. Диагностика указывает `step`: `verify-read-source/copy` — чтение исходника/копии, `set-copy-permissions` — установка прав копии, `after-permissions-read-source/copy` — повторное чтение после изменения прав, `service-read-access` или `service-write-probe` — проверка от пользователя сервиса. Поля `process`, `owner`, `mode` содержат только числовые UID/GID и права; приватные пути и содержимое не печатаются. Для разбора ошибки сохраните эту строку и название проверяемого volume. Не обходите проверку с помощью `chmod -R 777`.

При подготовке копии уже подходящие права не меняются: например, `0400` допустимы вместо `0444`, если права владельца совпадают, а права группы/остальных только строже. Это позволяет не выполнять лишний `chmod` для read-only объектов Git на файловой системе хоста. Необходимые изменения прав выполняются до смены владельца, дочерние записи — до каталогов. Проверки содержимого и фактического доступа пользователя сервиса остаются обязательными; отказ доступа по-прежнему останавливает перенос.
