# Orbit — контекст для продолжения разработки

Снимок контекста на **16 ноября 2026 года**. Это передача решений и истории работы
следующему агенту, а не полный транскрипт и не список поручений к немедленному выполнению.
Последнее проверенное состояние приложения: `master`, версия **0.72.3**, коммит
`efe270d`. Перед новой работой проверь фактические ветку, статус и HEAD: этот документ
со временем устареет. Новые указания пользователя имеют приоритет над историей здесь.

## Быстрый старт для следующего агента

1. Прочитай корневой [AGENTS.md](../AGENTS.md): это действующие правила работы.
2. Проверь `git status --short`, `git branch --show-current`, `git log -8 --oneline`.
   Не перезаписывай чужие незакоммиченные изменения.
3. Прочитай этот документ, [ARCHITECTURE.md](../ARCHITECTURE.md) и
   [правила справки](help/README.md). Для задачи найди соответствующую статью
   в `docs/help/articles` и реализацию. Старые формулировки из чата не заменяют код.
4. Уточни текущую задачу у пользователя, если она ещё не дана. Не начинай автоматически
   реализовывать все упомянутые ниже идеи и эксперименты.
5. Выполняй согласованные проверки и правила выпуска из AGENTS.md.

На момент передачи нет незавершённой реализации из последних двух задач:
исправления синхронизации PR и поля открытия тикета уже отправлены в `master`.

## Что такое Orbit

Локальное однопользовательское приложение для работы с Azure DevOps и GitHub Copilot.
Пользователь начинал с инструмента для лида, затем расширил его для разработчиков.
Ценность: тикеты, pull requests, код, AI-ревью, контекстная память, календарь,
локальные поручения и заметки в одном интерфейсе. Интерфейс и справка преимущественно
на русском; название продукта — Orbit.

Это уже рабочее приложение у нескольких людей. База, файлы, привязки, заметки,
история ревью и индивидуальные настройки ценны. Все изменения рассматриваются как
обновление заполненной установки. Нельзя сбрасывать данные ради исправления бага.

В старых голосовых сообщениях «ажур», «Jira DevOps», «AD/ADO» обычно означают
Azure DevOps, «UDiff/View diff» — просмотр diff PR. Не добавляй интеграцию Jira на
основании таких оговорок. «Lite/лит» в раннем обсуждении режимов стало текущим **Lead**.

## Как пользователь предпочитает работать

- Просьбы «давай», «можешь поправить» означают выполнить работу, а не только предложить план.
- Если сказано «сначала объясни», «пока обсуждаем» — сначала объяснить, код не менять.
- Пользователь не любит лишние подтверждения. Уточнять действительно недостающие
  решения, а обычные детали реализации решать самостоятельно.
- В истории есть постоянная просьба пушить завершённые изменения. Но явное
  «не пушить», название другой ветки или запрет коммита всегда важнее.
  Временные указания про `fsd` не означают пушить туда новые задачи сейчас.
- Короткие понятные обновления во время работы; в финале — результат, проверки,
  существенные ограничения и commit/branch, если был push.
- UI должен использовать общие компоненты: компактные селекты, цветные бейджи,
  круглые аватары с инициалами, одинаковые высоты полей, понятные действия.
  Пользователь особенно замечает отступы, переполнения, прыжки прокрутки и диалоги.
- В «Что нового» писать изменения поведения и возможностей, не каждый косметический
  штрих. Документацию обновлять вместе с функцией, не заменять её release notes.

## Основные продуктовые решения

### Контекст, подключения и режимы

Есть заказчик и проект Orbit, а также отдельные Azure URL/проект/репозиторий.
Проект может наследовать подключение заказчика/общих настроек либо иметь своё.
PAT Azure общий для приложения. Для фоновой операции с конкретным владельцем
использовать `store.settings({ client, project })`, а не `store.settings()` текущего
выбора в хедере. Не путать контекст отображения с владельцем выполняющейся операции.

Lead содержит весь продукт. Developer скрывает локальных разработчиков, поручения,
отпуска и относящиеся к ним UI/инструменты. Это не граница авторизации и не удаление
данных. Новые возможности по умолчанию доступны обоим режимам; исключать их из
Developer только по явной просьбе. Старые скрытые значения нужно сохранять.

Версия REST API Azure задаётся кодом, не редактируемой настройкой пользователя.
Пароль входа Orbit был убран; не возвращать его автоматически. Это не повод
ослаблять существующие ограничения API, CSRF или сетевую безопасность.

### Тикеты

- Есть локальный список, Azure-поиск и корзина; табличный и Kanban view.
  Настройки вида, фильтры и наборы сохраняются. Локальные поля нужно явно отличать
  от Azure: локальные теги, поручение, приоритет, дедлайн, заметки и даты.
- Автоимпорт определяет, какие новые тикеты попадают локально. Синхронизация уже
  импортированных тикетов не должна прекращаться только из-за смены исполнителя
  и выхода из фильтра автоимпорта. См. `ticket-sync.md`.
- Удаление локального тикета переносит его в локальную корзину, не удаляет в Azure.
  В UI есть подтверждения массовых действий; старые ограничения на распознавание
  явной команды ассистента для локальных операций не нужно возвращать без причины.
- Деталка открывается в строке или попапе; действие клика настраивается. Есть просмотр
  нескольких выбранных тикетов и история вложенных переходов с кнопкой назад/Escape.
- Содержимое включает описание, критерии приёмки, шаги воспроизведения и System Info
  при наличии. Важно одинаково поддерживать форматирование, изображения, кэш и поиск.
- Комментарии идут от новых к старым, редактор сверху. Заметки — отдельная вкладка
  с Markdown и явной кнопкой сохранения, без автосохранения.
- Связанные тикеты имеют тип, статус, исполнителя и тип связи. Фильтр по типу
  запоминается; если такого типа у следующего тикета нет, показывать «Все»,
  сохранив предпочтение для следующего подходящего тикета.
- Создание тикета доступно из хедера (настраиваемый хоткей, исходно Y) и переиспользуется
  для создания связанного тикета в боковой форме деталки. Созданный тикет импортируется
  локально. Важны одинаковые поля/редактор, прикрепление изображений для других людей,
  последний тип задачи и недавно выбранные исполнители. См. `tickets.md`.
- Azure-теги/приоритет редактируются через общие сценарии из таблицы и деталки.
  Статус при создании убрали из формы по отдельному решению пользователя.
- Экспорт: выбор/порядок столбцов, имя файла, копирование таблицы. Markdown и HTML
  для вставки в Teams/Excel — разные форматы буфера, их нельзя считать взаимозаменяемыми.

### Kanban

Столбцы отражают Azure-статусы; порядок, скрытые статусы и группы настраиваются
для проекта. Группе можно задать имя, цвет, входящие статусы и статус при переносе.
Фильтрация столбцов по фильтру статусов и скрытие пустых — отдельные настройки.
Перенос с изменением статуса Azure подтверждается и проверяется повторным чтением.

Фильтры/наборы общие с таблицей, есть сортировка и экспорт. Состояние «Спрятать
фильтры» сохраняется. Заголовки sticky, без двойной вертикальной прокрутки.
Уже несколько раз исправляли горизонтальную прокрутку macOS/Chrome и жест назад:
проверять обработчики wheel, preventDefault и overscroll совместно, не усиливать
скорость скролла и не добавлять scroll lock без согласования.

### PR и AI-ревью

- Мониторинг репозитория настраивается в заказчиках/проектах; фильтры Required,
  Optional, Created by. Есть активные, завершённые, входящие, точный просмотр по номеру.
- Связи PR/тикетов из Azure и локальные объединяются без дублей. Переход на PR
  должен работать внутри Orbit и сохранять доступ к истории ревью известных PR.
- Diff кэшируется по версии коммитов, а не сбрасывается при каждом открытии.
  Большие/исключённые файлы должны оставаться видны в дереве с причиной отсутствия
  содержимого. Переход из имени файла ведёт в код репозитория.
- Форма создания PR: репозиторий подписан, source-ветки показывают время обновления,
  название берётся из последнего коммита, на время загрузки блокируется поле,
  описание Markdown с изображениями. Изображения должны видеть и другие пользователи.
- В merge стратегия изначально не выбрана, кнопка недоступна до выбора. Сохранение
  локальных связей с тикетами в Azure — отдельная выключенная по умолчанию опция
  с выбором тикетов, без дублей. Не путать её со сменой статусов тикетов.
- Ревью показывает модель, токены и использованные вызовы инструментов/лимит;
  комментарий запуска спрятан за кнопкой, чтобы не раскрывать его при шаринге экрана.
- Ревьюеру нужны обоснованные замечания, значимые улучшения и нарушения памяти проекта,
  а также цитаты кода по делу. Не превращать ревью в перечисление каждой мелочи.
- Подробные правила памяти, календаря, экспорта и кода вынесены в описания лениво
  загружаемых инструментов. Не раздувать снова общий системный промпт.
  Архив правил: `services/backend/src/old-prompt.md`.
  `pr-review-system-prompt.example.txt` — исторический пример, не актуальный источник
  промпта и не файл для автоматической синхронизации.

### Календарь и напоминания

- Раздел имеет календарь и список, режимы день/неделя/месяц, общие фильтры/наборы,
  сохранение выбранного вида и фильтров, сортировку по ближайшей дате.
- В календаре есть временная сетка, линия «Сейчас», переход к текущему времени,
  перенос/изменение длительности с подтверждением. Часовые полосы чередуются
  по всей ширине недели, а не шахматами по отдельным дням.
- Напоминания бывают на дату, с окончанием, без времени, повторяющиеся с днями недели;
  уровни общий/заказчик/проект. Список и уведомления доступны независимо от хедера.
- Завершение — явное состояние, независимое от даты; можно вернуть в незавершённые.
  Для повторений различать текущую итерацию и всю серию. Не создавать новую сущность
  на каждый день. Завершённая сегодня серия остаётся доступной по фильтру повторений.
- Предупреждение заранее имеет общий срок и индивидуальное переопределение.
  Следующая итерация завтра может требовать предупреждения сегодня.
- Дедлайн тикета в календаре стоит на фактическом дедлайне, а не на времени начала
  предупреждения. До срока предупреждения он не появляется в уведомлениях.
  После срока статус меняется на просроченный без перезагрузки.
- Уведомления собираются по общему настроенному интервалу. Всплывающие карточки
  остаются до закрытия, имеют отдельные крестики и завершение с подтверждением.
  Закрыть карточку, завершить напоминание и скрыть его из уведомлений — разные действия.
  Завершение всей серии не должно быть лёгким случайным действием в угловом блоке.
- В деталке можно отдельно скрывать из календаря и уведомлений. Дедлайны показывают
  тикет и локальных исполнителей с аватарами. Отпуска — отдельный вид событий.
- Ассистент умеет искать, создавать и менять напоминания, включая повторения,
  безвременные, индивидуальные предупреждения и пакетные действия. Явные команды
  для напоминаний выполняются без цепочки перекрывающихся подтверждений.
  Для просьбы убрать напоминания о дедлайнах пользователь уточнил: завершать их,
  не очищать автоматически дедлайны тикетов.
- Напоминание об истечении PAT теперь тоже можно скрыть и задать отдельное предупреждение.
  Старое утверждение «его невозможно скрыть» отменено в 0.72.0.
  Оно остаётся производным от срока токена, а не обычным удаляемым/завершаемым событием.

### Разработчики, заметки, чат и голос

Разработчики привязаны к общему списку, заказчику или проекту. Есть локальные поручения,
заметки и один интервал отпуска с возможностью отмены. «Скоро в отпуск» в списках,
попапе поручения и поиске ассистента должно учитывать срок предупреждения календаря.
Текущий отпуск исключает разработчика из обычных вкладок активных/без активных.
Списки задач разработчиков показываются целиком без прежней пагинации по пять.

Свободные заметки и заметки тикетов доступны на странице заметок с Markdown и
изображениями. Неиспользуемые изображения нужно корректно убирать, не удаляя ещё
используемые файлы. Пользователь отменил идею инструментов свободных заметок для
чат-ассистента: не добавлять их по ранней просьбе из истории. Локальные заметки
тикета и существующие инструменты тикетов — отдельная область, сверять актуальную справку.

Чат должен сохранять правильный контекст проекта, не переносить чужой progress на
другой проект и восстанавливать живой ответ после перезагрузки. Память имеет разные
области; ассистент и PR reviewer имеют независимые Agent/session/cancellation.
Справка доступна через ленивые инструменты, не подмешивать весь каталог в каждый запрос.

Голос — отдельный сервис. Загрузка модели оставлена при первом обращении, не при
каждом build; она может долго идти, модель кэшируется. Обсуждали Electron/упаковку
без Docker, но это не означает, что такой дистрибутив реализован.

на первом этапе разбора. Регрессии: `tests/pr-project-sync.test.ts`.

Известны соседние проверки активного контекста в review worker `pull-requests.ts`.
В задаче 0.72.2 не делали полный рефакторинг ревью; при новом баге переключения
контекста проверять их отдельно, не считать всю область уже покрытой.

### Изображения Azure

Это многократно проблемная область. Различать `data:image/...`, браузерный `blob:`,
относительный `/UUID?fileName=...`, HTML `<img>` и Markdown `![]()`; браузерный blob
нельзя просто скачать с сервера как внешний URL. Поддержка inline data не равна
универсальной поддержке всех blob-ссылок.

Корпоративный прокси может показывать `dev.azure.com.mcas.ms`, когда API использует
`dev.azure.com`. Нельзя просто отключить проверку происхождения и пересылать PAT
на любой адрес. Нужны канонизация и подтверждение допустимого пути/коллекции/
проекта/репозитория/PR. WIT attachments и Git PR attachments — разные endpoint-ы.

Смотреть `azure-image-origin.ts`, `ticket-attachment-url.ts`, `pr-images.ts`,
`pull-requests.ts`, `connectors.ts`, frontend `features/render-content`.
Исторические баги: HTML-картинки пропущены; Unicode/encoded URL не совпал с renderer;
невидимый C0-символ у края URL; короткий путь вложения; project name vs GUID;
источник допустим, но preview потерян при рендеринге. При `different_collection`
или `different_project` нужны фактическая структура адреса, metadata и версия,
а не догадки по голосовой транскрипции. Не включать приватные URL/тела в документацию.

### Docker credentials — граница последнего решения

Ошибка `docker-credential-osxkeychain: executable file not found` возникает из
host Docker config, который ссылается на отсутствующий helper. Исправленная обёртка
`scripts/with-optional-docker-credentials.sh` помогает `update.sh`/установке и
явно обёрнутым командам, но **не исправляет глобально произвольный прямой
`docker compose up`**. Рабочие helpers и Docker config не переписываются.

Пользователь хотел вообще обходиться без скриптов. Объяснили: приложение/Compose
не может изменить проверку host Docker до запуска контейнера; нужна однократная
коррекция host config. Автоматическая глобальная правка не реализована.
Если эту задачу продолжать, учитывать `DOCKER_CONFIG`, сохранять backup/permissions,
`auths`, context, рабочие helpers и неизвестные ключи. Не удалять весь config и не
выдавать отсутствие credentials для приватного registry за успешную авторизацию.

## Экспериментальные ветки и отменённые идеи

На момент передачи локально существуют `fsd`, `group-test`, `group-view-test`,
`pull-request-create`, `secret-feature`, `ticket-create-update`, `master`.
Их наличие не доказывает, что каждая полностью влита; проверяй историю перед merge.

- Основной FSD-рефакторинг, создание/редактирование тикетов и создание PR развивались
  в отдельных ветках и затем переносились в master. Не начинать перенос заново по
  старому сообщению «продолжай».
- `secret-feature` — приветственные фейерверки; пользователь попросил оставить там
  и вернуться в master. Не переносить в основную ветку самостоятельно.
- `group-test` и `group-view-test` — эксперименты иерархии тикетов. В требованиях были
  разные редакции: в последнем эксперименте одноуровневая группировка по выбранным
  родительским типам, все children независимо от импорта/корзины и фильтров, ребёнок
  может повторяться под несколькими родителями; при раскрытии обновлять только детей
  этой группы, при сворачивании не запрашивать. Ранее обсуждалась другая фильтрация.
  Не смешивать эти варианты и не считать эксперимент включённым в master. Пользователь
  просил безопасный откат базы при возврате в master: изучить конкретные миграции
  ветки и существующие скрипты, не придумывать разрушительный rollback.
- Electron и единая desktop-упаковка всех сервисов обсуждались теоретически.
- Не восстанавливать автоматически отменённые идеи: пароль, загрузка voice-модели
  на build, инструменты свободных заметок для ассистента, редактируемая версия REST API.

## Проверки, релизы и сохранность данных

Полные правила находятся в AGENTS.md. Кратко:

- Для значимых/сквозных изменений: требования → разработка → UI/UX → независимые
  тесты через подагентов. Для маленькой правки допустим сокращённый процесс.
  Координатор владеет итоговым commit/push, агенты не меняют ветку сами.
- Prettier на изменённых поддерживаемых файлах, затем генерация справки, если менялись
  индексируемые исходники. Не форматировать runtime data и generated help вручную.
- `npm run check` обязателен: lint без warnings, format, FSD, releases, docs, TypeScript.
  Добавлять проверки поведения и миграций, а не тесты, зеркалящие очевидную разметку.
- При изменении данных нужны миграции/совместимые readers, повторный запуск и проверка
  заполненных старых данных. Для чистого изменения UI/документации фиктивная миграция
  не нужна. Не запускать тестовые миграции на пользовательской базе.
- Новая функциональная версия — одна запись newest-first на push, дата пользователя,
  соответствующие версии package/lockfile. Не переписывать опубликованные releases.
  Внутренняя документация без изменения продукта не требует bump версии.

```bash
npm run docs:generate
npm run docs:check
npx tsx --test tests/help.test.ts
npm run check
# По области изменения:
npm test
npm run build
```
