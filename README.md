# Orbit — персональный рабочий ассистент

Локальное однопользовательское приложение: GitHub Copilot, выбранные чаты Teams, Azure DevOps, три области памяти и голосовой ввод. Веб-интерфейс на русском. Данные сохраняются в Docker volumes.

## Запуск на Mac

Нужен работающий Docker Desktop (Apple Silicon или Intel), интернет и доступ к корпоративным сервисам/VPN.

```sh
docker compose up --build -d
```

Откройте **http://localhost:43871**, создайте локальный пароль (12+ символов) и настройте подключения. Порт опубликован только на `127.0.0.1`. Первая сборка скачивает зависимости; первое распознавание голоса скачивает мультиязычную модель Whisper `base`. Последующие запуски используют сохранённые слои и модель.

```sh
docker compose logs -f orbit voice
docker compose down
# Повторный запуск:
docker compose up -d
```

`docker compose down` сохраняет данные. **Не добавляйте `-v`, если не хотите удалить базу, ключ шифрования, состояние Copilot и модель Whisper.**

## Подключение GitHub Copilot

1. В Orbit → **Настройки → GitHub Copilot** нажмите **Войти через GitHub**. Client ID вводить не нужно.
2. Дождитесь одноразового кода, откройте предложенную ссылку и введите код. На стороне GitHub авторизуется **GitHub CLI**; подтвердите вход своим рабочим аккаунтом и запрашиваемые GitHub разрешения.
3. После подтверждения Orbit сохранит токен зашифрованным и загрузит доступные модели.
4. Выберите модель из выпадающего списка либо **По умолчанию в Copilot**, затем нажмите **Сохранить настройки**. Кнопка **Проверить и загрузить модели** обновляет список вручную. Если сохранённой модели нет в ответе, она отмечается как неподтверждённая.

GitHub CLI установлен в Docker-образе. Для запуска без Docker установите `gh` отдельно. Вход ограничен десятью минутами; после ошибки или перезапуска приложения начните его снова. CLI использует отдельную временную конфигурацию с доступом только владельцу: после чтения токена она удаляется, а токен хранится средствами Orbit. При аварийном завершении процесса временная папка может остаться в системном temp. Токен не передаётся браузеру и не попадает в журнал приложения.

Собственное OAuth App по-прежнему можно указать в **Дополнительно → Client ID** (нужен включённый Device Flow). Чтобы перейти со старого способа на вход GitHub CLI, очистите ранее введённый Client ID и нажмите кнопку входа. GitHub CLI использует свои стандартные OAuth-разрешения; проверьте их на странице согласия GitHub.

Используется официальный `@github/copilot-sdk`, без неофициального прокси Copilot API и без ключа другого модельного провайдера. Запросы используют вашу Copilot-подписку и её лимиты. Организация должна разрешать Copilot CLI/SDK и OAuth-приложение; SSO, IP-ограничения и прочие корпоративные правила продолжают действовать. Наличие подписки само по себе не гарантирует доступ приложению. При отзыве/истечении OAuth-токена войдите заново.

Справка: [поддерживаемые способы входа Copilot CLI](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference), [GitHub CLI login](https://cli.github.com/manual/gh_auth_login), [GitHub Copilot SDK OAuth](https://github.com/github/copilot-sdk/blob/main/docs/setup/github-oauth.md), [GitHub device flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow).

## Подключение Microsoft Teams

1. В Microsoft Entra admin center создайте App registration для своего корпоративного tenant, обычно single tenant.
2. Authentication → Advanced settings → **Allow public client flows: Yes**.
3. Добавьте **delegated Microsoft Graph permissions**: `User.Read`, `Chat.Read`, `ChatMessage.Send`. Не используйте application/migration permissions для обычной отправки.
4. Если политика организации требует admin consent, администратор должен одобрить эти разрешения. Conditional Access может запрещать device code flow; Orbit не обходит такую политику.
5. В Orbit → Настройки сохраните Directory/Tenant ID и Application/Client ID. Нажмите **Войти через Microsoft**, откройте страницу входа и введите код.
6. В разделе Teams нажмите **Загрузить чаты** и включите наблюдение за нужными. В Обзоре нажмите **Обновить** или дождитесь фоновой синхронизации.

При повторном входе используется выбранный Microsoft-аккаунт. Если аккаунт изменился, ожидающие черновики аннулируются, а список чатов очищается: загрузите и выберите чаты нового аккаунта заново.

Поддерживаются **личные и групповые чаты**. Каналы команд, вложения, реакции, упоминания с HTML-разметкой и редактирование отправленных сообщений в этой версии не реализованы. Исходящие сообщения — обычный текст. Первое чтение каждого чата импортирует последние 50 сообщений; последующие синхронизации листают страницы до последней отметки времени. При большом backlog или ошибке отметка не сдвигается, следующий проход безопасно повторяет импорт.

Справка: [чтение сообщений Graph](https://learn.microsoft.com/en-us/graph/api/chat-list-messages?view=graph-rest-1.0), [отправка сообщений Graph](https://learn.microsoft.com/en-us/graph/api/chatmessage-post?view=graph-rest-1.0), [MSAL Node](https://learn.microsoft.com/en-us/entra/msal/javascript/node/acquire-token-requests).

## Azure DevOps и нестандартный адрес

В Настройках задайте:

- **URL организации/коллекции**, например `https://dev.azure.com/my-org` или `https://devops.company.com/tfs/MyCollection`. Без имени проекта, `/_apis`, query-параметров и встроенных паролей. Требуется HTTPS.
- **Точное имя проекта** Azure DevOps.
- **PAT** с разрешением **Work Items (Read)**; для просмотра PR и их кода добавьте **Code (Read)**.
- **Версию API**: по умолчанию `7.1`. Для собственного Azure DevOps Server выберите поддерживаемую им версию.

Нажмите «Сохранить настройки», затем в Тикетах — «Импортировать мои» (WIQL `@Me`) или «Добавить по номеру». Трекер хранит локальную копию статуса, типа, исполнителя, заголовка и времени синхронизации. Рабочие элементы в Azure DevOps приложение не изменяет. Данные разных URL/проектов разделены ключом источника.

Из Teams извлекаются любые отдельные положительные целые числа, включая `123456`, `1234567` и короткие номера, а также `AB#123`, `#123`, «тикет №123», «bug 123», «work item 123». Дополнительно проверяются числовые фрагменты в HTTP(S)-ссылках и адресах HTML-ссылок: путь, параметры, fragment, в том числе `item123456/details` и URL-кодированные цифры. Скрытая за текстом «открыть» ссылка тоже учитывается; произвольные HTML-атрибуты и коды HTML-сущностей не считаются номерами. Нули и числа за пределами точного целого JavaScript исключаются, повторы объединяются. Это кандидаты, а не подтверждённые тикеты: даты, версии и другие числа тоже могут попасть во Входящие. При добавлении Orbit проверяет существование номера и выбранный проект через Azure DevOps; без успешной проверки тикет не сохраняется в трекере. Проверка не открывает найденную ссылку и использует только настроенный Azure API. Новое правило действует на сообщения, полученные при последующих синхронизациях; уже сохранённая история автоматически не пересканируется. Пользовательская регулярка не требуется и пока не добавлена. Все источники чатов относятся к выбранному Azure-проекту; для неоднозначных упоминаний пользователь проверяет проект перед добавлением.

Для частного центра сертификации смонтируйте PEM и задайте `NODE_EXTRA_CA_CERTS` контейнеру `orbit`. Не отключайте TLS-проверку. Доступ к внутреннему URL должен работать именно из контейнера (включая Docker/VPN DNS).

Справка: [Azure DevOps REST](https://learn.microsoft.com/en-us/azure/devops/integrate/how-to/call-rest-api?view=azure-devops), [PAT](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/use-personal-access-tokens-to-authenticate?view=azure-devops).

## Обязательное подтверждение отправки

```text
Запрос пользователя → Copilot → propose_teams_message
                                    ↓
                         неизменяемый черновик в SQLite
                                    ↓
                Получатель + полный текст в «Подтверждениях»
                                    ↓
                   Кнопка «Подтвердить и отправить»
                                    ↓
                       Graph POST /chats/{id}/messages
```

- У модели **нет инструмента отправки или подтверждения**. Она получает только явно перечисленные инструменты чтения, памяти и создания черновика.
- Copilot запускается в `mode: empty`; встроенные/MCP-инструменты, skills и обнаружение конфигурации отключены. Дополнительный pre-tool hook блокирует имена вне списка. Нет shell, произвольного HTTP или чтения файлов.
- Отправляющий HTTP-маршрут требует локальную аутентификацию, CSRF token, допустимый Host/Origin и специальный заголовок UI.
- Endpoint подтверждения не принимает новый текст или нового получателя. Изменить черновик — значит отклонить его и создать новый.
- В SQLite атомарно выполняется `pending → sending`: параллельный или повторный клик не отправляет второй раз. Черновик действует 24 часа.
- После успешного ответа Graph сохраняется ID сообщения. При неоднозначной сетевой ошибке или перезапуске в момент отправки статус — `unknown`; автоповтора нет. Проверьте Teams перед созданием нового черновика.
- Правила защищают от обхода **агентом**. Администратор машины с доступом к процессу/базе имеет контроль над приложением. Это локальный сервис одного доверенного пользователя, не многопользовательская платформа.

## Память и голос

В верхней панели выбирается заказчик и проект. Общая память доступна во всех контекстах; память заказчика — во всех его проектах; проектная — только для пары заказчик/проект. Записи можно добавлять вручную, сохранять по просьбе к агенту и удалять. История беседы разделена по тому же контексту. В контекст модели попадают до 40 последних сообщений и до 200 подходящих записей памяти; автоматического векторного поиска и бесконечной истории пока нет.

Микрофон работает по нажатию и выключается по кнопке либо через 2 минуты. MediaRecorder отправляет запись локальному voice-контейнеру с `faster-whisper` CPU/int8. Аудио не сохраняется приложением; распознанный текст появляется в поле ввода для проверки. В Copilot уходит текст только после отправки пользователем. Постоянного прослушивания, wake word и озвучивания ответов нет. Для браузерного микрофона нужен `localhost` или HTTPS.

Обработка аудио выполняется локально; **тексты запросов и запрошенный агентом контекст отправляются в GitHub Copilot**. Teams и Azure DevOps обслуживаются Microsoft/корпоративным сервером. Сохранённые OAuth-токены, MSAL cache и PAT зашифрованы AES-256-GCM; ключ `master.key` находится в том же volume и должен сохраняться вместе с базой. Это защита секретов от случайного чтения БД, не от владельца машины. Тексты сообщений, памяти и тикетов в SQLite не шифруются приложением — для защиты диска используйте FileVault.

## Разработка и проверки

Node.js 22 LTS рекомендуется (SDK требует Node 20.19+ или 22.12+). `.env.example` описывает переменные; приложение само `.env` не загружает — экспортируйте нужные значения в shell.

```sh
npm ci
npm run dev
# UI: http://localhost:5173, API: http://localhost:43871
npm run check
npm test
npm run test:sdk
npm run build
npm start
```

Для голоса при запуске Node без Docker запустите voice отдельно с портом на loopback:

```sh
docker compose run --rm -p 127.0.0.1:8000:8000 voice
```

`npm run test:sdk` дополнительно запускает настоящий runtime SDK с фиктивным токеном, выполняет разрешённый инструмент чтения и проверяет блокировку shell/approval. Модель при этом не вызывается.

Тесты не используют ваши аккаунты: проверяют обязательность апрува, конкурентные/повторные подтверждения, неоднозначную доставку, восстановление после перезапуска, изоляцию памяти, хранение секретов, Origin/CSRF, запрет встроенных инструментов и дедупликацию упоминаний.

Интеграционный прогон с реальными корпоративными аккаунтами выполняется после заполнения настроек. Для приёмки: загрузить модели → получить ответ ассистента → прочитать выбранный тестовый чат → импортировать реальный тикет → подготовить сообщение → убедиться, что до апрува оно отсутствует в Teams → подтвердить один раз → проверить ID/сообщение → попробовать повторный апрув (409) → проверить микрофон.

## Структура

- `src/` — React UI, голосовой ввод, экран подтверждений и подключения.
- `server/agent.ts` — системная политика и разрешённые инструменты Copilot.
- `server/approvals.ts` — конечный автомат доставки.
- `server/auth.ts` — GitHub device flow и MSAL.
- `server/connectors.ts` — Teams/Graph, Azure DevOps и извлечение тикетов.
- `server/store.ts` — SQLite, шифрование секретов, память.
- `server/app.ts` — аутентифицированный HTTP API.
- `voice/` — локальная транскрипция.
- `tests/` — проверки критических сценариев.

Пока нет push/webhook-уведомлений: по умолчанию синхронизация Teams и отслеживаемых тикетов запускается через 10 минут после завершения предыдущего прохода. В **Настройки → Как вам помогать → Обновлять Teams, тикеты и PR каждые, минут** можно установить интервал от 1 до 60 минут, в том числе 5 или 10, и нажать «Сохранить настройки». Новый интервал используется при следующем планировании без перезапуска; уже поставленный таймер завершится по прежнему расписанию. Первый проход после запуска приложения происходит через 10 секунд. При обновлении старое значение 5 минут один раз заменяется на 10 минут; другие интервалы сохраняются. Не реализованы каналы Teams, несколько одновременно подключённых Azure-проектов для тикетов (PR поддерживают несколько проектов одной коллекции), полноценное управление OAuth-аккаунтами (disconnect/revoke), импорт всех исторических чатов и редактирование произвольных полей рабочих элементов (смена статуса поддерживается). Фоновая синхронизация задач собирает данные без LLM. Мониторинг PR только обновляет список. Ревью ставится в очередь пользователем кнопкой.

Подробный отчёт о выполненных проверках и их границах: [docs/VALIDATION.md](docs/VALIDATION.md).

## Расход токенов и остановка агента

Экран **Использование LLM** показывает входные и выходные токены, кеш, количество пользовательских запросов и вызовов модели с отчётом SDK. Есть периоды 24 часа, 7/30 дней и всё время, журнал последних 100 запросов с результатом и причиной остановки. Суммы учитывают все запросы периода. Учёт хранится в SQLite и переживает перезапуск. Старые диалоги до установки трекера не пересчитываются.

Это расход только данного приложения, а не этого чата Codex, других Copilot-клиентов или всей корпоративной подписки. Число токенов не является счётом GitHub или остатком квоты. Используются события `assistant.usage`; повторные отчёты дедуплицируются, кеш не прибавляется повторно. Отсутствие статистики обозначается явно. При ошибке, отмене или перезапуске отчёт может быть неполным и фактический расход выше.

В **Настройках → Как вам помогать** доступны ограничения на один запрос:

- Время: по умолчанию 180 секунд (15–600).
- Вызовы инструментов: по умолчанию 20 (1–100); следующий вызов запрещается и агент останавливается.
- Мягкий порог входных + выходных токенов: по умолчанию 100 000 (1 000–1 000 000). Проверяется после получения usage, поэтому уже выполняющиеся вызовы могут превысить порог. Без usage работают ограничения времени и инструментов.

Кнопка **Остановить ответ** находится в панели ассистента; текущий запрос также можно остановить на экране расхода. Остановка вызывает abort, а при задержке — принудительное завершение локального SDK runtime. Уже выполненные действия (например, запись памяти или создание черновика) не отменяются, потраченные токены не возвращаются. Остановка локального процесса не гарантирует мгновенную отмену уже принятого сервером вызова. Новые настройки применяются к следующему запросу.

Один ответ может включать несколько обращений к модели. История и память снова передаются в контекст, что увеличивает входные токены. Контекст истории/памяти ограничен 90 000 символов, ответ отдельного инструмента — 24 000; это ограничения размера, а не точная токенизация. Автоматическое расширение сессии и компактация отключены. Одновременно приложение выполняет только один пользовательский запрос; автоматического повторения запросов на уровне приложения нет. Опрос Teams/тикетов и обновление счётчика в UI не вызывают LLM. Ручное PR-ревью вызывает модель только после нажатия кнопки запуска.


## Заказчики и проекты

Верхняя панель содержит два выпадающих списка. Выберите заказчика, затем его проект; переключение сохраняется сразу, статус сообщает «Контекст сохранён». При ошибке прежний контекст остаётся активным. **Общий контекст** использует общую память; **Без проекта** добавляет память выбранного заказчика. Выбор проекта добавляет его память и отдельную историю диалога.

Кнопка **Заказчики и проекты** открывает список всех заказчиков и их проектов, формы добавления и кнопки переключения. **Добавить и выбрать** сохраняет новую запись и активирует её. Одинаковые названия проектов допустимы у разных заказчиков; повторы внутри одного заказчика объединяются. Существующие контексты из истории, памяти и сохранённых настроек доступны в списке. После перезапуска выбор сохраняется. Переименование и удаление контекстов пока не реализованы.

Это контексты ассистента: они не меняют подключение Teams или проект Azure DevOps. Последний задаётся отдельно в настройках интеграции.


## Работа без Teams и автоматический импорт задач

Teams необязателен. Переключатель **Настройки → Microsoft Teams → Читать Teams в фоне** по умолчанию выключен, даже если ранее выполнялся вход. Без его включения фоновая синхронизация не обращается к Graph. Старые сохранённые чаты и ручные операции остаются доступны; приложение ничего не отправляет без отдельного апрува.

Для основного проекта задач в **Настройки → Azure DevOps**:

1. Укажите URL коллекции, проект и PAT с Work Items (Read).
2. Нажмите **Сохранить подключение и загрузить типы / статусы**.
3. Выберите реальные типы вашего процесса (например, Bug и Change Request) и нужные статусы.
4. Включите **Автоматический импорт** и сохраните настройки.

Каждый проход выполняет WIQL-запрос с `Assigned To = @Me` (владелец PAT), выбранным проектом, типами и статусами. Новые совпадения добавляются в трекер без LLM. Уже добавленные тикеты не удаляются при выходе из фильтра: их статусы продолжают обновляться. Пустые фильтры не означают «всё»: включение автоимпорта с пустыми типами/статусами отклоняется. Фильтр применяется к Azure-проекту из настроек, а не к названию контекста ассистента.

## Карточки тикетов в чате

Запрос «Покажи тикет 123456» получает данные непосредственно из Azure, даже если тикета нет в трекере. Модель также имеет инструмент `get_ticket` для уточняющих запросов по номеру. Чтение карточки не добавляет задачу в трекер. В разделе **Тикеты** есть отдельное поле открытия карточки без обращения к модели.

Карточка содержит описание, шаги воспроизведения, критерии приёмки, раскрываемый список всех полей, комментарии с пагинацией и вложения. Полная карточка сохраняется как снимок вместе с датой получения и ссылкой в истории чата; для обновления запросите тикет повторно. HTML показывается безопасным текстом. Для LLM содержимое ограничивается размерами контекста, но карточка в UI не обрезается этим лимитом.

Изображения из вложений и текста Azure отображаются в UI через авторизованный локальный прокси. PAT не передаётся браузеру. Загрузка разрешена только для зарегистрированных в карточке вложений из настроенной коллекции, без перехода по редиректам; файл ограничен 20 МБ. Внешние изображения других сайтов не загружаются, SVG и прочие активные форматы скачиваются как файлы. При смене подключения старую карточку нужно загрузить заново для доступа к её вложениям. Пиксели изображений модели пока не передаются: это просмотр изображений человеком, а не визуальный анализ LLM.

Comments API некоторых Azure DevOps Server может быть недоступен. Тогда карточка явно сообщает, что комментарии получены не полностью. Защитный предел — 10 000 комментариев; достижение лимита также отображается. История изменений полей и удалённые комментарии отдельно не загружаются.

## Pull requests: репозиторий проекта и ручное ревью

В «Заказчики и проекты» или на вкладке PR задайте Azure Project и точное имя/ID Git-репозитория для выбранной пары заказчик/проект Orbit. Используется URL организации/коллекции и PAT из настроек. При сохранении нового подключения для того же контекста прежние подключения отключаются; сохранённые PR и результаты остаются доступны.

Синхронизация раз в 10 минут (настраивается) читает только активные PR выбранного репозитория. Фильтр — все либо только личное назначение владельца PAT как required reviewer; группы не учитываются. **Синхронизация не вызывает модель.** Новые коммиты также не запускают ревью. Старые автоматические задания в очереди отменяются при первом обновлении на эту версию.

Кнопка «Запустить ревью» ставит конкретную версию PR в очередь. Обработчик ждёт свободную модель и соблюдает суточный лимит. Повторное нажатие не создаёт дубликат; успешное ревью той же версии повторно не запускается. Ошибку можно повторить вручную. Черновики и PR вне текущей выборки не запускаются. «Сохранённые ревью всех версий» показывает прежние итоги даже после новых коммитов или смены фильтра.

Ревью получает общую память, память заказчика и проекта, с общим пределом до 200 записей и 90 000 символов; историю личного чата не получает. Инструменты записи и shell недоступны. Анализируется diff между merge base и source commit, результаты сохраняются только в Orbit. Лимиты: 100 файлов, 50 000 символов на файл, 80 000 символов diff; пропуски указываются в покрытии. Тесты кода PR не запускаются, комментарии/голоса/merge в Azure не выполняются.

## Локальный трекер тикетов

В таблице доступны сортировки по ID, названию и статусу, просмотр полной карточки и «Убрать из списка». Удаление локальное: тикет исключается из последующих импортов, но не удаляется в Azure. Явное добавление по номеру возвращает его в трекер.

«Локально поручено» — отдельное назначение в SQLite, не поле Assigned To Azure. Кнопка загрузки участников получает людей из команд настроенного Azure-проекта (Core Teams API; PAT может потребовать Project and Team: Read). Группы не разворачиваются. Назначение сохраняется при синхронизации и повторном добавлении тикета; исходный исполнитель Azure показан отдельно. Список участников изолирован по подключению/проекту.

Цвета точных названий статусов задаются в настройках Azure → «Цвета статусов» и применяются к таблице и карточкам. Описание, критерии приёмки, комментарии и вложения имеют независимые раскрывающиеся секции. Внешнего аккордеона карточки нет.

## Смена статуса тикета через чат

Команда: **«Переведи тикет 123456 в RFT»**. Агент использует отдельный инструмент `change_ticket_status`; детерминированная процедура находится в `server/ticket-status.ts`, а Azure-адаптер — в `server/connectors.ts`. Устанавливать отдельный skill или запускать shell-скрипт не нужно.

1. Читается актуальный тикет, проверяются номер и настроенный Azure-проект.
2. Загружаются статусы именно этого типа задачи. Используется точное имя без учёта регистра; `RFT` сопоставляется с `Ready for Testing`, если собственного статуса `RFT` нет. Неизвестные или неоднозначные названия отклоняются со списком допустимых.
3. Отправляется JSON Patch только для `System.State`, с проверкой `/rev`. Правила переходов и обязательных полей Azure не обходятся.
4. Выполняется отдельный GET. Успех возвращается только если фактический статус точно совпадает с целевым. Если он уже был таким, запись вообще не выполняется.

Если PATCH завершился ошибкой, процедура всё равно читает актуальный статус: совпадение означает «статус подтверждён, результат самой записи неизвестен», а не гарантированно выполненный нами переход. Если GET недоступен или статус не совпадает, успех не возвращается. Автоповтора PATCH нет. Повторные вызовы инструмента для того же тикета внутри одного ответа используют сохранённый результат/ошибку; для следующего перехода нужна новая команда.

Для смены статусов PAT должен иметь **Work Items (Read & write)**. Дополнительный UI-апрув для этой операции не требуется: основание — явная команда пользователя с номером и целевым статусом. Сервер проверяет текущую команду; содержимое тикетов не может само разрешить запись. В фоновом PR-ревью инструмент недоступен. Уже отслеживаемый тикет обновляется локально, факт проверки попадает в журнал, карточка в чате по возможности обновляется. Чтение неполной карточки после подтверждённой смены статуса не отменяет успешную операцию.
